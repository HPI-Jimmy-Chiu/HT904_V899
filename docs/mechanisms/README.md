# Mechanisms（機構契約層）

> 跨機台、跨版本、跨實作風格的「機構契約」集中地。
> 每份 mechanism 描述**一個物理機構**的不變量（invariant）、狀態機骨架、安全規則。
> 不綁變數名、不綁檔名、不綁實作風格。

---

## 為什麼有這層

過去的 SPEC（`docs/spec/modules/`）綁住了單一機台的命名與檔案結構。
當下一個專案要複用同樣的物理機構時，工程師（或 AI）必須：
- 重新讀程式碼確認動作順序
- 自己決定要抄 HT9045 風格還是 HT172 風格
- 自己判斷哪些是「機構必然」、哪些是「歷史寫法」

**Mechanism 契約**把這些決策前置到文件裡：

```
┌─────────────────────────────────────────────────────────┐
│  L0 機構契約（本資料夾）                                     │
│  - 物理動作順序                                              │
│  - 不變量與安全規則（標共通性等級 ????）                  │
│  - 狀態機 case 編號契約                                      │
│  - 角色 sensor / actuator 清單（不綁名）                      │
│  - 驗證 checklist                                            │
└─────────────────────────────────────────────────────────┘
                  ↑                      ↑
        ┌─────────┴────────┐  ┌─────────┴──────────┐
        │  HT9045 實作對照   │  │  HT172 實作對照     │
        │  docs/implementa  │  │  docs/implementa   │
        │  tions/HT9045-... │  │  tions/HT172-...   │
        └──────────────────┘  └───────────────────┘
```

## 共通性等級（Universality Tag）

每條規則必須標其中一個：

| 標籤 | 意義 | Port 新機台時 |
|------|------|--------------|
| ? **物理必然** | 機構物理結構決定，不可能變 | **必須遵守** |
| ? **跨機驗證** | 已在 ?2 個機台驗證過的慣例 | **強烈建議遵守** |
| ? **公司慣例** | HT 系列內部歷史共識 | **建議遵守** |
| ? **單機特例** | 只在某機台出現的特殊處理 | **不要照抄** |

## 命名規範

```
mechanisms/
  <機構家族>-<驅動方式>-<能力>.md
```

範例：
- `stacker-cylinder-separator.md` = 堆疊區 + 汽缸驅動 + 分離爪（可上下分堆）
- `stacker-cylinder-stackonly.md` = 堆疊區 + 汽缸驅動 + 只能往上堆（未來）
- `stacker-motor-separator.md` = 堆疊區 + 馬達驅動 + 分離爪（未來）

---

## 文件結構模板

每份 mechanism 必須包含：

1. **§0 機構身份與適用範圍**
2. **§1 物理組成**（哪些零件，圖示）
3. **§2 不變量**（標共通性等級）
4. **§3 狀態機契約**（case 編號區段語意）
5. **§4 角色清單**（sensor / actuator / flag 的角色，不綁名）
6. **§5 安全規則**
7. **§6 對外交握介面**（可被誰呼叫、會通知誰）
8. **§7 驗證 checklist**（人工或工具用）
9. **§8 已知實作對照表**（連結到 implementations/）
