## 2. Tester 介面模式盤點（本機 recipe 全覽）

模式碼（`cmydef.h:48-51`）：`TTL_MODE=0`、`GPIB_MODE=1`、`RS232_MODE=2`、`TCP_IP_MODE=3`（讀自各 recipe 的 `Tester.Data` → `[Mode] Tester Type`，`cTesterIF.cpp:572`）。

掃描 `IniData\Data\` 下 **54 個 recipe**：

| Tester Type | 模式 | recipe 數 | Handler 端 64-bit | 範例 recipe |
|:-----------:|------|:--------:|:-----------------:|-------------|
| 1 | GPIB_MODE | **50** | 🟢 外部 GPIB 橋（`D:\GPIB9045`），WM_COPYDATA | R003_MT6899_HOT…（現行）、多數 |
| 2 | RS232_MODE | **3** | 🟢 序列 COM | D169_LQFP256_28X28_2X2_SLT1_25_V03、LQFP64_10X10_125、LQFP48-7X7-125 |
| 3 | TCP_IP_MODE | **1** | 🟢 TCP sockets（OS-Tester WORKFILE 交握）| LS7A2000BC-29X29-958-2.407 |
| 0 | TTL_MODE | **0** | （未使用）| — |

**結論**：本機所有 recipe 的 tester 介面（GPIB/RS232/TCP）在 Handler 端**全部是綠燈**，不引入任何 32 位元廠商 DLL，因此 **tester 介面對 64 位元不是阻礙**，與選哪個 recipe 無關。

> 備註：GPIB 橋接程式（`H9046_32GPIB.exe`）本身是獨立的 32 位元程序，與 Handler 之間走 `WM_COPYDATA`。`WM_COPYDATA` 可跨 32/64 位元程序傳遞，故 64 位元 Handler 仍能與 32 位元 GPIB 橋通訊；惟需確認 payload 結構不含指標/`size_t` 寬度假設（橋接協定為字串式，風險低）。

## 3. 廠商 / 內部需求清單

### A · CONTEC（SMC 運動主控）— 廠商已有 64-bit
- [ ] 64-bit（x64）API-SMC(WDM) 套件：簽章 x64 WDM 驅動（`CSmc.sys`）、x64 `CSMC.dll`、x64 COFF import lib、對應 `CSmc.h`/`CSmcdef.h`。
- [ ] 確認實機卡型（板上 SMC-xxxx 料號）仍在現行 64-bit 驅動的 Support Device 清單，非 EOL。
- [ ] x64 驅動是否 WHQL/Attestation 簽章（Secure Boot／簽章強制下可載入），Win11 IoT LTSC 安裝程序。
- [ ] x64 標頭核對：`SmcW*` 的 pulse/position/count 參數是否維持 C `long`（LLP64 仍 32-bit）。
- [ ] 事件函式（`SmcWStopEvent`/`SmcWCountEvent`）的 `CSMC_MESSAGE(0x8700)` WPARAM/LPARAM 在 x64 的編碼。

### B · ICP DAS（MN200 MotionNet — 機台 IO）— 需先確認卡是否存在
- [ ] **先確認**：本機是否真有獨立 ICP DAS MotionNet（MN200/PISO-MN200/PCIe-MN200）卡負責那 389 個 IO 點，還是 IO 實際走 SMC 卡（兩份分析在此點有分歧，須實機接線/裝置管理員確認）。
- [ ] 若有：取 64-bit `MN200DLL.dll`（或 PCIe-MN200 SDK）＋ x64 import lib ＋ 簽章 64-bit PCI 驅動；確認 `mn_set_port_bit`/`mn_get_port_bit` API 一致。
- [ ] 若該卡 EOL 無 64-bit：評估換 PCIe-MN200（ICP DAS 有 64-bit 路徑），並對應 `MyLaneIo.cpp` 的 IO 呼叫層。

### C · 自家 RD（KeyPro 加密狗）— 內部可控，需重設計介面
- [ ] 原生 x64 KeyProDLL（PE `0x8664`），對同一顆實體 USB dongle 有效；若有 kernel 驅動需 64-bit 簽章版。
- [ ] **純 C ABI 標頭**（移除所有跨 DLL 邊界的 `std::string`）：
  - `int KEYPRO_GET_ID(char* buf, int len)`
  - `int KEYPRO_GET_ERROR_CODE(char* buf, int len)`
  - `int KEYPRO_GET_DATE_INFO(char* y, char* m, char* d, char* useDay, int len)`
  - `bool KEYPRO_WRITE_ID_INOF(const char* sID)`
  - 呼叫端配置緩衝 → 無 allocator 跨界（去掉 `borlndmm` 相依）。`KEYPRO_GET_LEVEL(unsigned)->int` 已是 C 安全，僅需 64-bit build。
- [ ] 64-bit import lib 格式（MS COFF .lib 或 DLL+.def 供自建），支援 LoadLibrary/GetProcAddress。
- [ ] 確認 64-bit DLL 不再相依 Borland/Delphi RTL；既有出貨 dongle 與新 SDK 前向相容（免換狗）；`KEYPRO_GET_LEVEL(3)==1` 的 SECS/GEM 啟用語意保留。

> **最小可行**：906 目前只呼叫 `KEYPRO_GET_LEVEL`（純整數，C 安全），所以「先能在 64-bit 過 license」其實只需該函式的 x64 build。`std::string` 全面重設計是為了日後和 HT70XX 別版統一，可分階段。

## 5. 為什麼是路線 B（而非移植到 Visual C++）

路線 B 與「移植到 Visual C++（MFC）」的**硬體 64-bit 工作完全一樣**（都得換 CONTEC/KeyPro 等的 64-bit binary）。差別只在：B 把整個 UI、事件模型、字串方法、133 個表單、`AnsiString`、所有名稱原樣保留；移植到 MSVC 則額外多了一個數人年的 UI 重寫，且會部分犧牲「名稱一致」。既然工具不拘、又要名稱一致，MSVC 沒有任何相對於 B 的好處，只有額外成本。

| 路線 | 保留 VCL/名稱 | 達成 64-bit | 主要工作量 | 風險 |
|------|:---:|:---:|------|:---:|
| A. C++Builder（維持 32-bit）| ✓ 全保留 | ✗ 非 64-bit | 小：重編＋Clang 修正 | 低 |
| **B. C++Builder（Win64）← 採用** | ✓ 全保留 | ✓ 本機可行 | 中：A＋每個硬體相依換 64-bit | 中（受 2 個廠商項）|
| C. 移植到 Visual C++ / MFC | ✗ UI 全重寫 | ✓（同樣硬體工作）| 極大：133 表單＋字串＋執行緒＋IPC 全重寫（數人年）| 高 |

## 9. 介面切割設計（HAL — 先切後接）

策略：用介面把「物理控制」切出來，先以 **stub/模擬實作** 讓 64 位元版**現在就能編譯、連結、離線執行**（不需實機）；之後有實機時，再把各接縫的 **real 64-bit 實作**逐一換入、邊測邊接。原則：**盡量沿用程式裡既有的抽象與名稱**（新類別只增不改），符合「名稱反查 BCB 版本」。

### 9.1 五個接縫現況與切法

| 接縫 | 既有抽象 | 切法 | 工作量 |
|------|---------|------|:------:|
| 運動 | ✅ **已是虛擬基底** `HTMotor`（~50 virtual）+ 品牌子類；單一 dispatch 在 `cinitial.cpp` | 加 `TMySimMotor : HTMotor`，在 dispatch ladder 加一個 `"SIM"` 分支（或全域 `bOfflineSim`）。real 64-bit 實作日後逐軸由 `Mot_Table.csv` CardModel 切換，**不需重編**。| 低 |
| 數位 IO | ❌ `TLaneIO` 具體單例，方法內 switch | 抽出 `TIOBackend` 虛擬基底；把 3 行 vendor 分派搬進 `TMN200Backend`/`TPci1203Backend`/`TMnetLegacyBackend`/`TSimIOBackend`；`TLaneIO` 留原名當門面、持 `pBackend`。**上百個 TMySwitch/Sensor/Cylinder/Sucker 呼叫點完全不動**。| 中 |
| KeyPro | ❌ 自由函式 + 靜態 `#pragma link` | 改 `LoadLibrary`/`GetProcAddress` shim，只解析 `KEYPRO_GET_LEVEL`；DLL 缺席時 stub 回 1。呼叫點只改一行。| 低 |
| Tester | ❌ switch-on-typecode；**OFF_LINE 模擬已存在**(data-flag) | 加 `ITesterInterface` 基底 + `cTesterGPIB`/`cTesterTCP`/`cTesterTTL`/`cTesterSim`（把現有 OFF_LINE/`SimulateBin()` 升級成類別）。| 高 |
| 全域模擬 | `SOFT_SIMULTE`（編譯 macro，~966 處/154 檔，預設關）| 見 9.3 兩階段；**注意它只 disable、不 unlink** 32-bit vendor libs。| 中 |

### 9.2 各接縫關鍵點（含 file:line）

- **運動（最佳情況）**：`HTMotor`（`Motor/HTMotor.h:31`）已是乾淨多型基底；`TMyMotor` 內含 `HTMotor* Motor` 轉發；dispatch 唯一處在 `cinitial.cpp:3454-3565`（CardModel 字串 + `INDEX_MOTION_CARD==0` Galil 分支 3464-3482）。只要新增 `TMySimMotor`（覆寫 `ReadPos/MoveToPos/MotionDone/HomeObject/HomeFlag/GetAlarm/ScanMotorStatus` 回成功＋假位置）並在 ladder 加一分支即可。real 64-bit 先換最可能就緒的 `TMyEtherCatMotor`(Advantech)/`TMySMCMotor`(CONTEC)。
- **IO**：實際 vendor 呼叫只在 `TLaneIO` 的 6 個方法內各 3 行（`MyLaneIo.cpp:143-158/210-225/278-292/397-412/466-481`）。抽 `TIOBackend{ WriteBit/ReadBit/WriteByte/ReadByte }`（回 int，<0=fail，沿用現 `ret` 慣例），range/error/OutPortData 記帳留在 TLaneIO。raw-port（`myio.cpp:107-296` 的 `outportb/inportb`+EnableNTPort，x86-only）以 `TRawPortBackend` 或 `#ifdef` 收斂為 no-op。
- **KeyPro**：唯一呼叫 `KEYPRO_GET_LEVEL(3)` 在 `HS_Function.cpp:4933`(CheckKeyPro)。新增 `Public/HTKeyProShim.h/.cpp`，`int KeyPro_GetLevel(unsigned)`；移除 `#pragma link "KeyProDLL.lib"`(HS_Function.cpp:46) 與 .bpr 連結項。`__stdcall` 匯出名可能是 `KEYPRO_GET_LEVEL` 或 `_KEYPRO_GET_LEVEL@4`——以 tdump/dumpbin 確認後 GetProcAddress。
- **Tester**：dispatch 在 `atester.cpp`（`iTestType` × `LastSet.iTester`）。三種傳輸：GPIB→32-bit 橋(WM_COPYDATA)、TCP→VCL TClientSocket、TTL/RS232→DIO 卡/外部 RS232Standard.exe。OFF_LINE 模擬已在 `TesterTCP.cpp:249-267/537-554`。新增 `ITesterInterface{ Find/RunTestProgram/SendMSG_CMD/CloseGpibProgram/GetTesterResult }`，4 個子類各轉發到既有程式碼。

### 9.3 兩階段執行（對應「先切後接」）

1. **Tier 1 — 最快讓 64-bit 離線版能跑**：先開 `SOFT_SIMULTE`（`MachineType.h:43` 取消註解），它已串過五個子系統的離線行為。**但它不解除 32-bit vendor lib 的連結**，所以為了 64-bit「連得起來」，仍須把 vendor `#include`/`#pragma link`/殘留呼叫包進 sim 實作，或做一支 64-bit import-stub lib 滿足符號。KeyPro 在非 SECS 離線版本不需動（CheckKeyPro 受 SECS gate）。
2. **Tier 2 — 逐接縫換真實硬體（真正的介面切割）**：運動已多型 → 加 `TMySimMotor` + dispatch 分支即可，之後每軸由 `Mot_Table.csv` 從 SIM 翻成 real 64-bit 子類，**免重編**。IO/Tester 先抽出小虛擬基底再加 sim 子類。整套維持 pre-C++11/VCL（純 virtual、AnsiString，不用 std::function/lambda/auto），與既有 `HTMotor` 模式一致。

### 9.4 跨位元地雷（務必先修）

64-bit Handler 仍可與 **32-bit GPIB 橋**透過 WM_COPYDATA 溝通——但 `MessageDef.h` 的 `MV`/`VM` 結構內嵌 `HWND`（`HandlerHwnd`/`GpibHwnd`，第 259-260 行）。HWND 為指標寬度，`sizeof`/欄位 offset 在 32/64 位元不同，會讓跨位元 payload 錯位。**動 64-bit Handler 接 32-bit 橋之前，須把這些 HWND 欄位改成固定寬度**（如 `DWORD` + `HandleToLong`）或移出 WM_COPYDATA 結構。扁平的 `M_V`(`InterfaceSYS.h:222`，只有 Byte/unsigned int/char) 才跨位元安全。

### 9.5 與增量上機的對應

- **現在（無實機，64-bit）**：全部選 sim 實作 → 編譯/連結/離線執行，可先驗證整個 64 位元移植（UI、邏輯、狀態機）與硬體無關。
- **之後（實機）**：逐接縫換 real 64-bit 實作，邊接邊測——先 CONTEC SMC（運動，廠商有 64-bit）、再 MN200 IO（若有）、Galil index（若有）、KeyPro（自家 64-bit SDK 到位後），全在同一介面後面切換，呼叫端不動。
