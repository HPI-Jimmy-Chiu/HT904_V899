## 1. 設計原則（為什麼這是最穩定的作法）

1. **不做整檔自動轉譯。** C++→C# 轉譯器對 VCL + 直接操作硬體 I/O + 全域狀態機的程式，產出「能編譯但行為不可信」的程式碼，對安全關鍵機台不可接受。
2. **不動最危險的東西。** 真正的硬即時在運動控制卡（Galil DMC、SMC、MN200…）上，PC 端是「軟即時編排」。保留 native 即時/IO 核心 = 把最高風險區隔離在已驗證的 C++ 之外。
3. **每一步都有黃金基準。** 既有 BCB6 build 是行為基準；每個搬移的模組都要對比通過才算數。
4. **一次搬一個葉節點。** 從非即時、低耦合模組開始，逐步往核心推進，永遠保持「可隨時回退到 C++ 版」。
5. **編碼邊界單一化。** Big5 `AnsiString` 只在檔案/IO 邊界轉碼，C# 內部一律 UTF-16。

## 3. 模組搬移優先序（風險由低到高）

| 波次 | 模組 | 即時性 | 耦合度 | 風險 | 說明 |
|------|------|--------|--------|------|------|
| W1 | 報表 / 資料分析 / log 解析 | 無 | 低 | 低 | 純資料處理，最佳 PoC 起點 |
| W1 | 設定載入（cinitial 的 ini/csv/dat） | 無 | 中 | 低 | 欄位順序敏感，需嚴格對拍 |
| W2 | LotInfo 批次管理 | 無 | 中 | 中 | FTP/Recipe 下載、批次持久化 |
| W2 | SECS/GEM 訊息組裝 | 軟 | 中 | 中 | 須維持 SEMI 合規格式 |
| W3 | UI 對話框（逐個 .dfm 重畫成 WinForms） | 無 | 中 | 中 | 無法自動轉，手動重建 |
| W4 | 流程編排狀態機：CatchTray → Shuttle → InArm/OutArm → Index | 軟即時 | 高 | 高 | 一次一個，每個都要上機驗證 |
| — | 運動控制 / 低階 IO / 互鎖 / 安全 | 硬即時 | — | — | **不搬，保留 native** |

> 推薦 PoC 試點：**報表/資料分析模組**——零即時性、可直接拿舊 log 對拍、能完整驗證「C# ↔ SQLite ↔ 檔案編碼」全鏈路，又不碰硬體。

## 4. 分階段執行計畫

### Phase 0 — 凍結與特徵化（基礎，先做）
- [ ] 將 899 BCB6 build 訂為黃金基準，鎖版本目錄（其他版本維持唯讀）。
- [ ] 蒐集真實機台 log（Task_ListWithTime、EventLog、state record）建立**行為特徵化測試集**。
- [ ] 盤點全域狀態：`MachineType.h`、`cprod.h`、`cpublic.h`、`cmydef.h` 的全域變數清單與跨模組依賴圖。
- [ ] 盤點 native 驅動 API 介面（CSMC / DMC32 / MN200 / KeyPro）作為接縫設計輸入。
- **出場條件**：有一套可重播、可比對的回歸基準。

### Phase 1 — 建立凍結互操作接縫
- [ ] 設計 `HwInterop` C-ABI 介面（純 C 函式簽章，無 C++/VCL 型別跨界）。
- [ ] 包裝運動/IO/互鎖/授權呼叫，C++ 與 C# 皆可呼叫。
- [ ] C# 端建立 P/Invoke 包裝與型別封送（marshalling）規範。
- [ ] 確立編碼轉換工具：Big5 ↔ UTF-16 單一邊界函式。
- **出場條件**：C# 能透過接縫成功讀取 IO 狀態、觸發一個無害動作並比對結果。

### Phase 2 — 搬移非即時葉節點（W1–W2）
- [ ] PoC：報表/資料分析模組轉 C#，對舊 log 對拍通過。
- [ ] 設定載入轉 C#，與 cinitial 逐欄位對拍（ini/csv/dat 順序敏感）。
- [ ] LotInfo、SECS/GEM 訊息組裝轉 C#，SEMI 格式逐筆驗證。
- **出場條件**：非即時模組在 C# 與 C++ 並行下行為一致。

### Phase 3 — UI 重建（W3）
- [ ] 逐個 `.dfm` 重畫為 WinForms（不自動轉，手動重建 + 行為對照）。
- [ ] UI 透過接縫與既有核心通訊，可與舊 UI 並行驗證。
- **出場條件**：關鍵操作畫面以 WinForms 可完成等價操作。

### Phase 4 — 搬移流程編排狀態機（W4）
- [ ] 依序 CatchTray → Shuttle → InArm/OutArm → Index，一次一個。
- [ ] 每個狀態機搬移後過特徵化測試 + **上機驗證**才收尾。
- [ ] 全域狀態先切出明確邊界（避免把耦合帶進 C#）。
- **出場條件**：編排層在 C# 運行，native 僅剩即時/IO/安全核心。

## 5. 關鍵風險與對策

| 風險 | 影響 | 對策 |
|------|------|------|
| `.dfm` 無法自動轉 | UI 全部需重畫 | WinForms 心智模型最接近 VCL；逐表單手動重建並對照 |
| 全域變數深度耦合 | 搬移時把整包耦合帶入 | 搬移前先畫依賴圖、切邊界，必要時先在 C++ 端封裝 getter/setter |
| Big5 / AnsiString 編碼 | 中文亂碼、log 解析錯誤 | 內部統一 UTF-16，僅 IO 邊界轉碼，加入亂碼（U+FFFD）檢查 |
| 授權 `KeyProDLL` | 啟動驗證失效 | 經接縫呼叫，不重寫驗證邏輯 |
| SECS/GEM 格式走樣 | 違反 SEMI、客戶端不相容 | 逐訊息對拍既有封包，保留變數命名 |
| 封送（marshalling）錯誤 | interop 記憶體/型別崩潰 | 接縫只用簡單 C 型別，建立封送單元測試 |
| .NET GC 抖動 | 編排層延遲 | 即時核心留 native；C# 編排層避免熱路徑配置，必要時 Server GC |

## 6. 不做什麼（明確排除）

- ❌ 不用自動轉譯器整檔轉換。
- ❌ 不搬運動控制 / 低階 IO / 互鎖 / 安全核心（保留 native）。
- ❌ 不修改驅動與定義檔（CSMC.h、sqlite3.h 等 AGENTS.md 禁改清單）。
- ❌ 不在計畫階段同時動多個模組——一次一個，可回退。
